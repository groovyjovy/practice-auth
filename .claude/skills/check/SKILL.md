# コードレビュー

対象: `$ARGUMENTS`(空なら直近に変更されたファイル。`find . -newer PROGRESS.md -not -path './node_modules/*'` などで特定する)

## 手順

1. 対象ファイルをすべて読む。`memo.md` から該当フェーズの「作るもの」と「説明できるようになること」を確認する
2. 以下の観点でチェックする(該当フェーズに関係するものだけ)

### 共通
- 秘密情報のハードコード、ログへの出力
- 入力検証の欠如、型の `any` / 非 null アサーションでの逃げ
- エラーレスポンスが内部情報(スタックトレース、ユーザー存在有無)を漏らしていないか

### フェーズ別の重点
- **1**:ハッシュのパラメータ(scrypt の N/r/p、ソルト長)、`timingSafeEqual` の長さ不一致時の扱い、セッション ID のエントロピー、ログイン時の ID 再生成、Cookie 属性、ログアウトでサーバー側を消しているか、ユーザー列挙
- **2**:base64url の実装(パディング、`+/`)、署名比較が定数時間か、`alg` をヘッダから信じていないか、`exp` / `nbf` / `iat` の検証、`aud` / `iss` の検証
- **3**:`redirect_uri` 完全一致、認可コードの単回使用と短い有効期限、コードと `client_id` / `redirect_uri` の紐づけ、PKCE(S256 のみ許可しているか、`code_verifier` の長さ)、`state` の生成と検証、client 認証、エラーレスポンスの形式(RFC 6749 §4.1.2.1 / §5.2)、scope の検証、トークンの `Cache-Control: no-store`
- **4**:ID トークンのクレーム(`iss`, `sub`, `aud`, `exp`, `iat`, `nonce`)、`kid` と JWKS、クライアント側の検証漏れ
- **5**:Discovery の取得とキャッシュ、`jose` の使い方(`algorithms` の指定、`issuer` / `audience`)
- **6**:認可チェックの漏れ(全ルートで `can()` を通っているか)、IDOR、デフォルト許可になっていないか
- **7**:チャレンジの単回使用、`origin` / `rpID` の検証、signCount

3. 結果を以下の形式で返す。**修正後のコードは書かない**

```
## 重大度: 高
- `path:line` 何が問題か(1 文)
  - 攻撃シナリオ: 誰がどう悪用できるか
  - 調べるもの: RFC xxxx §y.z / OWASP ○○
  - 問い: 本人に考えさせる質問

## 重大度: 中 / 低
...

## よく書けている点
- 1〜2 個。理由つきで
```

4. 指摘が攻撃で実証できるものなら「`/break` で実際に突いてみる?」と提案する
5. `--save` が指定されたときだけ、`reviews/YYYY-MM-DD-<対象>.md` に結果を保存する
6. 重大な指摘がなく、そのフェーズの「作るもの」が揃っていれば `PROGRESS.md` の該当項目にチェックを入れ、`/quiz` を勧める
