# 段階的ヒント

相談内容: `$ARGUMENTS`

## 原則

- 答えのコードは書かない。本人が書けるところまで導く
- エラーが出ているなら、まずエラーメッセージと関連ファイルを自分で読み、**原因の位置** を特定してから答える(推測で答えない)
- 1 回の返答で出すヒントは 1 レベル分だけ。次のレベルが欲しければ本人がもう一度聞く

## レベル

指定がなければ、同じ話題で何回目の質問かから判断する(初回はレベル 1)。

1. **方向性**:何を考えればよいか、問題をどう分解するかを問いかけで示す。関係する概念名を挙げる
   - 例:「セッション ID の生成で大事な性質は何だと思う? 予測できてはいけない理由を考えてみて」
2. **具体的な道具**:使う API / 関数名、公式ドキュメントのページ、仕様の節を示す。引数や戻り値の型など「調べれば分かること」のありかを示す
   - 例:「`node:crypto` の `randomBytes` のドキュメントを見て。何バイトにするかは OWASP Session Management Cheat Sheet の Session ID Entropy の節」
3. **擬似コード / 構造**:処理の流れを日本語の箇条書きか、ごく粗い擬似コードで示す。実際の TypeScript は書かない

レベル 3 の後も詰まっていて、本人が明示的に「答えを見せて」と言った場合のみ、**該当箇所の最小限の数行** を見せてよい。その場合も、なぜそう書くのかを本人に説明させる問いを添える。

## 環境構築の相談

- 環境構築は本筋ではないので、段階的ヒントにせず、必要なコマンドや設定をそのまま示してよい
- 本人に頼まれたら、設定ファイルの作成やコマンドの実行も Claude が行ってよい

## 締め

ヒントの最後に、本人が次に確認すべきこと(「これで○○が返るはず」)を 1 つ書く。
